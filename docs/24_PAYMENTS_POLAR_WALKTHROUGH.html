3a · Checkout route (server-resolved, client picks only a pack name)

Don't use the query-param adapter that trusts client-supplied product IDs — accept only ?pack=100|250|700 and resolve the product server-side. Attach the Supabase user as externalCustomerId so the webhook can credit the right account without trusting metadata alone.

src/app/api/checkout/route.ts 
import { NextResponse } from "next/server";
import { Polar } from "@polar-sh/sdk";
import { enforceLimits } from "@/lib/security/rateLimit";
import { getSupabaseServerClient } from "@/lib/supabase/server";

const PACKS: Record<string, string | undefined> = {
  "100": process.env.POLAR_PRODUCT_100,
  "250": process.env.POLAR_PRODUCT_250,
  "700": process.env.POLAR_PRODUCT_700,
};

export async function GET(req: Request): Promise<NextResponse> {
  await enforceLimits(req, "checkout"); // add "checkout" to RouteKind — see 3c

  const token = process.env.POLAR_ACCESS_TOKEN;
  const productId = PACKS[new URL(req.url).searchParams.get("pack") ?? ""];
  if (!token || !productId) {
    return NextResponse.json({ error: "PAYMENTS_UNCONFIGURED" }, { status: 503 });
  }

  const supabase = await getSupabaseServerClient();
  const { data: { user } = { user: null } } = (await supabase?.auth.getUser()) ?? {};
  if (!user) return NextResponse.redirect(new URL("/login?next=/pricing", req.url));

  const polar = new Polar({
    accessToken: token,
    server: process.env.POLAR_SERVER === "production" ? "production" : "sandbox",
  });
  const checkout = await polar.checkouts.create({
    products: [productId],
    externalCustomerId: user.id,          // ← how the webhook finds the user
    customerEmail: user.email ?? undefined,
    successUrl: new URL("/pricing?checkout=success", req.url).toString(),
    metadata: { userId: user.id },        // belt-and-braces fallback
  });
  return NextResponse.redirect(checkout.url);
}

3b · Webhook route (the only place coins are credited)

The Webhooks helper verifies the signature before your handler runs, and it needs the raw body — so don't wrap this route in anything that parses JSON first. Credit only on order.paid; the DB's unique index on order_id makes retries a no-op.

src/app/api/webhooks/polar/route.ts 
import { Webhooks } from "@polar-sh/nextjs";
import { getSupabaseServiceRoleClient } from "@/lib/supabase/admin";

const COINS_BY_PRODUCT: Record<string, number> = {
  [process.env.POLAR_PRODUCT_100 ?? "?100"]: 100,
  [process.env.POLAR_PRODUCT_250 ?? "?250"]: 250,
  [process.env.POLAR_PRODUCT_700 ?? "?700"]: 700,
};

export const POST = Webhooks({
  webhookSecret: process.env.POLAR_WEBHOOK_SECRET ?? "",
  onOrderPaid: async ({ data: order }) => {
    // Field names: log the payload ONCE in sandbox and pin them against the
    // SDK types — expected: order.id, order.productId (or order.items[n]),
    // order.customer.externalId, order.metadata.
    const userId =
      order.customer?.externalId ?? (order.metadata?.userId as string | undefined);
    const coins = COINS_BY_PRODUCT[order.productId ?? ""];
    if (!userId || !coins) {
      console.error("[polar] unmapped order", order.id, order.productId, userId);
      return; // 200 anyway — never make Polar retry an unfixable payload
    }
    const admin = getSupabaseServiceRoleClient();
    if (!admin) throw new Error("service role missing"); // 500 → Polar retries
    const { error } = await admin.from("coin_ledger").insert({
      user_id: userId,
      delta: coins,
      bucket: "purchased",
      reason: "order",
      order_id: order.id,
    });
    // 23505 = unique violation on coin_ledger_order_uidx → retried delivery,
    // the coins are already credited. Anything else should 500 so Polar retries.
    if (error && error.code !== "23505") throw new Error(error.message);
  },
});

3c · Small supporting edits

  • Rate limiter: add "checkout" to RouteKind in src/lib/security/rateLimit.ts with a modest per-minute cap (it's a DB-only route — follow the publish entry's pattern; env knob RL_CHECKOUT_PER_MIN). The webhook route gets no rate limit — Polar retries on failures and signature verification is the gate.
  • /pricing buttons: in src/app/pricing/page.tsx, swap the disabled button for a link to /api/checkout?pack=100|250|700. Gate on auth the same way START does (signed-out → the existing "Sign up first" modal). Keep rendering the disabled "coming soon" state when payments aren't configured — add NEXT_PUBLIC_PAYMENTS_ENABLED=true (build-time, same pattern as NEXT_PUBLIC_COINS_ENABLED) so you can deploy the code before flipping it on.
  • Success state: on /pricing, read ?checkout=success → show a toast and fire window.dispatchEvent(new Event("ada:coins-changed")) so the header chip refetches. The webhook usually lands within a couple of seconds of the redirect; refetch once more after ~3 s to cover the race.

Pitfalls — read before writing code

The five ways this goes wrong
  • Trusting the client: the browser only ever sends a pack name. Product IDs, prices, and coin amounts live server-side. Never read a coin amount from checkout metadata that the client could have set.
  • Crediting on the wrong event: only order.paid credits coins. checkout.updated fires for states that never get paid.
  • Breaking idempotency: keep order_id on the insert and treat 23505 as success — Polar redelivers webhooks on any non-2xx.
  • Slow webhook: answer fast, no provider calls, no heavy work — insert one row and return. Timeouts look like failures and cause retries.
  • Forgetting the redeploy: NEXT_PUBLIC_* flags are inlined at build time. Changing them in Vercel without a redeploy does nothing (you learned this with the coins flag).
